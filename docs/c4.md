# C4 Model – Home Meal Planning System

This document describes the system using the **C4 model**, focusing on the **Context** and **Container** levels, which are appropriate for the scope of this TFM.

---

## Level 1 – System Context

### Purpose

The **Home Meal Planning System** helps households reduce time and cognitive load related to:

- deciding what to cook each day
- managing home food inventory
- generating shopping lists to avoid waste and missing ingredients

The system acts as a decision-support backend rather than a simple recipe or inventory application.

---

### People

**Household User**
- Manages the household inventory
- Requests daily meal suggestions
- Accepts a recipe suggestion for the day
- Generates shopping lists when ingredients are missing
- Accesses the system through the current Web Demo

**Admin (future)**
- Operational support and monitoring
- No admin interface implemented in the current scope

---

### External Systems

**PostgreSQL Database**
- Stores users, households, inventory, recipes and meal suggestions
- Accessed via Prisma ORM

Future external systems (not implemented):
- Supermarket integrations
- Notification services

### Context Notes
- The system is currently consumed through a Web Demo.
- The Web Demo is designed as a mobile-first interface with two main sections:
     - **Plan**
     - **Inventory**
- The architecture remains backend-first, with a clean separation of concerns.

## Level 2 – Container Diagram

### Containers Overview

The system is composed of the following main containers:

---

### 1. Web Demo (React + Vite + Tailwind)

**Responsibilities**
- Authenticate users
- Store short-lived access token in frontend
- Trigger silent refresh using refresh cookie
- Present the application through a mobile-first UI
- Organize the experience in two tabs:
     - **Plan**
     - **Inventory**
**Main screens**
- Login/Register view
- Plan tab
- Inventory tab

---

### 2. HTTP API (Fastify)

**Responsibilities**
- Expose REST endpoints (JSON over HTTP)
- Validate input/output using Zod schemas
- Handle authentication and authorization
- Map requests to application use cases

**Implemented endpoints (summary)**
- Auth:
     - `POST /auth/register`
     - `POST /auth/login`
     - `GET /auth/me`
     - `POST /auth/refresh`
     - `POST /auth/logout`

- Inventory:
     - `POST /inventory/update`
     - `GET /inventory`

- Plan / Suggestions
     - `POST /suggestions/generate`
     - `GET /suggestions/daily`
     - `POST /suggestions/modify`
     - `POST /suggestions/accept`
     - `POST /plan/today`

- Ingredients:
     - `GET /ingredients/search`
     - `GET /ingredients/by-ids`
     - `POST /ingredients`

---

### 3. Application Core (Domain + Use Cases)

**Responsibilities**
- Encapsulate all business rules
- Orchestrate domain logic via use cases
- Remain independent of frameworks and infrastructure

**Implemented Use Cases**
- UpdateInventoryUseCase
- GenerateDailySuggestionUseCase
- GenerateShoppingListUseCase
- GenerateShoppingListFromRecipesUseCase
- GenerateAndStoreDailySuggestionUseCase
- AcceptSuggestionUseCase
- ModifySuggestionUseCase
- GetCookingPlanUseCase

---

### 4. Infrastructure Layer

**Responsibilities**
- Implement repository interfaces (ports)
- Handle persistence and database access

**Technology**
- Prisma ORM
- PostgreSQL

**Repositories**
- PrismaInventoryRepository
- PrismaRecipeRepository
- PrismaSuggestionRepository

---

### 5. Contracts Package

**packages/contracts**

**Responsibilities**
- Define request/response schemas
- Provide runtime validation (Zod)
- Share TypeScript types between backend and clients

Acts as a single source of truth for API contracts.

### Key Architectural Decisions

- **Clean Architecture** ensures that business logic is isolated from frameworks and infrastructure.
- **Prisma ORM** provides safe persistence and schema migrations.
- **Zod contracts** enforce runtime validation and shared API definitions.
- **JWT + refresh token in httpOnly cookie** improves security and session UX.
- The frontend is now intentionally **mobile-first**, prioritizing the daily plan as the main entry point.

## Level 3 – Component Diagram (HTTP API / Fastify)

### Responsibilities
- Accept HTTP requests
- Validate input/output using shared Zod contracts
- Map contracts ↔ application DTOs
- Invoke application use cases
- Return HTTP responses
- Enforce auth and household access

### Main components

#### 1) Routes / Controllers (Fastify handlers)
- Define endpoints and bind them to handlers

#### 2) Validation Boundary (Contracts)
- Uses `packages/contracts`
- Validates requests and responses with Zod

#### 3) Mappers
- Transform contract DTOs ↔ use case DTOs

#### 4) Auth layer
- `requireAuth(...)`
- household access assertions
- refresh/logout routes

#### 5) Composition Root (Manual DI)
- `server.ts` creates and wires:
- repositories
- use cases
- route handlers
